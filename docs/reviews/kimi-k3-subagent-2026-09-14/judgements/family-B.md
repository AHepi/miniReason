## Family-level reading

Across these four occasions the worker's **reading and diagnosis were its strength and its oracles were its weakness, and the two were never tested against each other because it almost never got to run anything.** It reads the module, the design entry, both notes and the house-style exemplars before writing, and then goes past the brief into the real dependency — b-03 followed `Situation.from_harness` into `deepreason_core/ontology/state.py` before building a fixture. It executes constructed inputs rather than reciting: b-01 computed a byte offset of 101 against a code-point index of 91 through the module itself. It corrects itself against tool errors within one turn (b-04 pass 2: "No shell — each command runs alone"). And it declines to invent: faced with an unimportable module it wrote, rather than a guess, "the wave-0 siblings minireason.loop.types / minireason.loop.contracts are not copied here, so this oracle cannot run" (b-02, `test_seats.py:17-25`). The countervailing weakness is that an assertion it has not executed is frequently wrong about the bytes it names — b-02's `assertIn('importlib.import_module("tools.multicycle_commitment_study_multi_v2")', source)` asserts a line `seats.py` does not contain, and seven `Endpoint(...)` calls omit the required `base_url`. Two habits compound it: it reports a blanket skip as OK instead of leaving the failure visible, and when a command misbehaves it suspects the environment before its own command form — b-02 spent iterations 20-40 building a shadow `_scratch/` tree to fix an `exit_code: 1` that its own `| tail -30` had produced.

Three infrastructure effects must be held apart from all of that. **First, the per-turn cap ends runs silently.** In pass 2 and pass 3 every family-B run that the harness labelled `COMPLETE` ended on a turn of exactly 8,192 completion tokens, `finish_reason: "length"`, empty content, no tool calls, with ~33,000 characters of reasoning and nothing else; `files_written` is `[]` and the final message is `""`. The label is a harness artifact — pass 3's SUMMARY.md records four COMPLETE tasks and "(none)" written for all four — and any reading of this family that treats COMPLETE as delivery is wrong. **Second, b-02's sandbox omits the module's own imports.** `seats.py:102-103` imports `.contracts` and `.types`; neither is in the task's `context_paths`, nor is `tools/multicycle_commitment_study_multi_v2.py`. The project's own withheld suite fails there identically (`Ran 1 test / FAILED (errors=1)`), so the one task that produced an artifact is the one that could not have produced a green non-vacuous suite. **Third, the passes failed for unrelated transport reasons** — pass 1's three gateway closures and pass 2's HTTP_500 — which say nothing about the worker. What survives all three: `src/` is byte-identical to `battery/material` in all nine sandboxes, so gate 4 holds without exception, and the refusal to edit the module under test was never tested by temptation, because no run ever reached a red test.
