1. **Count is not reset when a slot is confirmed, so finite tau values expire prematurely.**

### 1. The tie among `tau` values on H_neutral is a mathematical necessity of the code, not an empirical finding
**Claim attacked:** “on a one-thing world with no occlusion, persistence values tau=0,2,5,inf tie exactly”.

**Why it fails:**  
In `reconcile_slots`, an unconfirmed slot is immediately offered to any occupied cell within `radius`:
```python

              if s is not None and not confirmed[i] and abs(s["cell"] - c) <= radius]

    ...

```
The drop condition is:
```python

    for i, s in enumerate(self.slots):
        if s is not None and s["count"] > tau:

```
On H_neutral there is one thing and no occlusion. For `num_cells=6`, the grammar allows `radius=5`, which covers the entire line. Any displacement can therefore be immediately re-bound in the same reconcile step, resetting `count` to 0 before the drop condition is ever checked. `tau` never sees `count > 0`. **Severity:** serious — the neutrality check is vacuous.

**Fix:** Use a world where `radius` cannot cover the maximum displacement (e.g. larger `num_cells` or a smaller maximum radius), or include occlusion in the neutrality history, or explicitly state that the tie is a trivial consequence of immediate rebinding.

### 2. `thing_signature` manually injects the change into the predictor, making `tau=inf` pass trivially

### 4. Binding establishment in `thing_signature` selects only already-perfect cases and ignores spare slots
**Claim attacked:** the thing-signature test establishes bindings in a way that guarantees passing.

**Why it fails:**

### 5. The lookup “longest available prefix” is not implemented — exact key or zero, no backoff
**Claim attacked:** the lookup uses the “longest available prefix”.

**Why it fails:**  
`lookup_key` returns only the current buffer:
```python
def lookup_key(self):
    if not self.a["use_lookup"] or not self.buffer:
        return None
    return tuple(self.buffer)  # longest available prefix, at most k fields
```
and `predict` does:
```python
key = self.lookup_key()
if key is not None:
    bits |= self.table.get(key, 0)
```
If the exact full-length key is absent from the table, the code contributes 0. It never falls back to a shorter prefix that might be present. For `k=3`, many 3-field keys will be unseen in the exposure half, and the lookup will return 0 even when a 2-field or 1-field key was learned. This unfairly penalizes lookup architectures, especially as `k` grows, and can make slot-only appear better in the adequacy comparison.

**Severity:** serious — it biases the lookup-vs-slot comparison.

**Fix:** Implement true backoff: try the full buffer, then drop the oldest field and retry, until a key is found or the buffer is empty. For example:
```python
key = tuple(self.buffer)
while key:
    if key in self.table:
        bits |= self.table[key]
        break
    key = key[1:]
```

## 1. `thing_signature` writes the world's answer into the model, so passing is a fixpoint property, not a measurement (fatal)

```

The slot is teleported to the exact post-change cell and given the exact post-change velocity. The predicate then checked is

```

i.e. exact `(cell, velocity)` equality with the hidden world state. and `count` is reset to 0 in the snap branch (`s["count"] = 0`) and in the creation branch (`"count": 0`). With `READ_IN_RULES` containing `radius in (2, 5)` and `num_cells = 6`, radius 5 means `abs(s["cell"] - c) <= radius` holds for **every** pair of cells in the world (max distance 5). In the one-thing world exactly one slot is ever created (creation happens only for an *unmatched* occupied cell, and the single occupied cell is either matched by the confirmed slot or snaps to the unconfirmed one), so at every reconcile either `count` is reset to 0 or the incrementing slot is always a snap candidate. Result: `count > tau` is never satisfied, for any `tau ≥ 0`, and the rules `persist(0,5,F)`, `persist(2,5,F)`, `persist(5,5,F)`, `persist(inf,5,F)` (and their `jump_keeps=True` twins) are **bit-identically** the same function. If the per-persistence argmax picks `radius=5` — which the exact tie strongly suggests — the tie is a property of the grammar, not of the world. `H_neutral` has no `occlude` in its change set (`{"identity", "displace", "set_velocity"}`), and the `displace` targets are all within radius 5, so nothing rescues the tau path.

**(3) Severity.** Fatal for the neutrality check as stated.

**(4) Fix.** Instrument the removal line (count how often `s["count"] > tau` fires per persistence value on `H_neutral`) and report it. Report the argmax `(num_slots, radius, jump_keeps)` per persistence value, not just the name. If the argmax radius is 5, say so and either restrict the grammar to `radius=2` (where `count` can exceed `tau`, since 3-cell displacements exceed 2) or delete the neutrality claim.

## 5. The neutrality check silently drops `rebind`, contradicting its own docstring (serious — moved goalpost)

**(1) Claim attacked.** `"""Neutrality: on H_neutral, the best architecture for each persistence value (rebind, tau=0, 2, 5, inf) all within 0.01 of each other."""`

**(2) Why it fails.**

```
tau_vals = [v["fitness"] for pv, v in out["H_neutral_best_per_persistence"].items() if pv != "rebind"]
out["neutrality_check_passes"] = (max(tau_vals) - min(tau_vals)) <= 0.01
```

`rebind` is computed (it is in the loop over `("rebind", "tau=0", ...)`) and then excluded from the test. The criterion as designed cannot fail for the reason the design gives. The comment at the top of the function, `"""Section 5 / section 8 step 2 of the design (as amended)"""`, is an unattributable appeal: the amendment is not in the file or the design text I can check.

**(3) Severity.** Serious (the check is weaker than advertised).

**(4) Fix.** Either include `rebind` or state, in the design document, the amended criterion and why `rebind` is excluded.

## 6. The adequacy criterion is half-implemented (serious)

**(1) Claim attacked.** `"""Adequacy: on H_full, best slot-only > best lookup-only and >= 0.95 * ceiling."""`

**(2) Why it fails.** The code computes

out["adequacy_check_passes"] = f_s > f_l
out["H_full_best_slot_fraction_of_ceiling"] = f_s / out["ceiling_H_full_evaluation_half"]

The 0.95 clause is never evaluated; a ratio of, say, 0.4 would still emit `"adequacy_check_passes": true`. A design criterion can be loosened only openly.

**(3) Severity.** Serious.

**(4) Fix.** Compute and record both booleans, or retract the 0.95 clause in the design document.

## 7. "Best lookup-only" is a structurally crippled baseline, so `f_s > f_l` is guaranteed a priori (serious confound)

**(1) Claim attacked.** The "object-model axis" (`best slot-only > best lookup-only`) and the comparison of lookup fitness to the ceiling.

**(2) Why it fails.** Four independent handicaps are stacked on the lookup:

- It is a *suffix*, not a prefix, and mislabelled: `return tuple(self.buffer)  # longest available prefix, at most k fields`. `self.buffer` holds the last `k` fields.
- No back-off: if the `k`-tuple is unseen, the query does not fall back to shorter keys, even though the table contains keys of every length 1..k.
- The default is a constant zero: `bits |= self.table.get(key, 0)`. For these worlds a zero field is never the correct continuation, so every unseen key is a guaranteed error. A fairer baseline would default to the marginal/majority continuation.
- Training is `table[key] = seq[t + 1]["true"]` (last-writer-wins) for keys that collide across change types, whereas `sensory_ceiling` uses a majority vote with a different tie-break (`max(c.items(), key=lambda kv: (kv[1], -kv[0]))`). The two are compared as if they were the same learner.

**(3) Severity.** Serious: the "lookup loses to object model" result is an artefact of the baseline's construction.

**(4) Fix.** Add back-off, a majority-vote table, and a non-degenerate default; report the fraction of evaluation keys unseen. Then compare.

## 8. The sensory ceiling is an in-sample oracle on the evaluation half, and the comparison mixes protocols (serious)

**(1) Claim attacked.** `"""...This is the best deterministic predictor from sensation on this history, and an upper bound for every architecture."""` and its use as the denominator of the adequacy ratio.

**(2) Why it fails.** It is a valid upper bound *for the evaluation half*, but it is fitted on the same data it is scored on:

```
for _, _, seq in history:
    for t in range(RUN_LENGTH):
        key = tuple(s["sensory"] for s in seq[:t + 1])
        counts.setdefault(key, defaultdict(int))[seq[t + 1]["true"]] += 1
best = {key: max(c.items(), ...) ...}
...
    ok = best[key] == seq[t + 1]["true"]
```

whereas the architectures' tables are fitted on the *exposure* half (`expose_lookup(a, exposure, num_cells)`). Also, in `main` it is computed as `sensory_ceiling(split[name][1])`, i.e. only on the odd half, which is the same half used for model selection (finding 11). Finally, the ceiling is a full-prefix memoriser while the lookup is a ≤k-window model, so the "object-model axis" is contaminated by a memory-capacity difference. Whether the resulting bias is conservative (oracle high) or not, the two numbers are not on the same footing and the ratio has no clean interpretation.

**(3) Severity.** Serious for the "fraction of ceiling" and adequacy claims.

**(4) Fix.** Report (a) the eval-half oracle (current number, labelled as an oracle), (b) a ceiling learnt on the exposure half and scored on the eval half, and (c) the step-wise breakdown. State explicitly that the ceiling has unbounded memory.

## 9. `M2` for `H_full` is literally `M1` for `H_full` (serious — duplicated metric presented as a second measure)

**(1) Claim attacked.** The two metrics `M1` and `M2`, and the "contract generalisation" reading of `M2`.

**(2) Why it fails.**

```
"H_full": (6, 2, {"identity", "displace", "set_velocity", "occlude", "swap"}),
...
full_contract = {1: build_history(6, 1, {"identity", "displace", "set_velocity", "occlude"}),
                 2: build_history(6, 2, {"identity", "displace", "set_velocity", "occlude", "swap"})}
```

`full_contract[2]` is built with exactly the change set of `H_full`, and the same `enumerate_changes`/`enumerate_configurations` order, so `full_eval[2]` is content-identical (and order-identical) to `split["H_full"][1]`. In the row loop the *same* `table` object is used for both:

```
table = expose_lookup(a, exposure, num_cells)
m1, _ = evaluate(a, table, evaluation, num_cells)
m2, m2_by_type = evaluate(a, table, full_eval[num_things], num_cells)
```

Hence `M1["H_full"] == M2["H_full"]` exactly, including `by_type`. This is verifiable in `results.json`. Any text that treats M1 and M2 as two lines of evidence for the 2-thing case is double-counting one number.

**(3) Severity.** Serious.

**(4) Fix.** Deduplicate (report once), or give `M2` a contract whose change set and configuration set genuinely differ from `H_full`.

## 10. Model selection and the evolutionary "confirmation" both run on the evaluation half (serious — selection-on-test)

**(1) Claim attacked.** "We then ask which architectures each history selects" and "whether a blind mutation-selection search lands on the same architectures", with `results["protocol"] = "exposure on even-index configurations; every fitness is on the odd-index half"`.

**(2) Why it fails.** The exposure/evaluation split protects only the lookup table. The architecture is chosen by maximising on the *same* odd half that the reported fitness is computed from:

```
best = max(r["M1"][hname] for r in table_rows)
selected[hname] = {"max_fitness": best, "architectures": [...]}
```

and the evolutionary loop optimises the same quantity:

```
exposure, evaluation = split_history(history, num_cells, num_things)
def fitness(a): ... fitness_cache[key] = evaluate(a, table, evaluation, num_cells)[0]
```

So "best of 208 architectures on the odd half" and "the search lands on the same architecture" are not independent facts; the search's objective *is* the reported statistic. There is no third split.

**(3) Severity.** Serious.

**(4) Fix.** Three-way split (exposure / selection / confirmation) or nested CV; report selection-half and confirmation-half fitness separately, and report the selection-half max alongside the winner's confirmation-half fitness.

## 11. `swap` is observationally identical to `identity` (serious — one of the five conditions tests nothing)

**(1) Claim attacked.** The inclusion of `"swap"` as a change condition, and any reported `by_type["swap"]` accuracy or `thing_signature` swap pass.

**(2) Why it fails.**

```
elif kind == "swap":
    things[0], things[1] = things[1], things[0]
```

`occupancy_bits` ORs the cell bits (order-independent) and `step_kinematics` is applied per element, so the multiset of thing states evolves identically after a swap. The `sensory` and `true` sequences for a `swap` change are therefore bit-for-bit identical to the `identity` sequence for the same configuration. Consequences: (a) `by_type["swap"] == by_type["identity"]` for every architecture — check it in the JSON; (b) the `H_full` history contains each identity sequence twice, so the "do nothing" condition is double-weighted in every aggregate metric; (c) in `thing_signature` the swap case flips the binding by bookkeeping only (`binding = {slot: 1 - thing for slot, thing in binding.items()}`) while the slot states are untouched, so the swap case passes for any rule that passes identity — the advertised "identity tracking" evidence is vacuous.

**(3) Severity.** Serious (a whole condition is a no-op, presented as one of the contract's discriminators).

**(4) Fix.** Make swaps observable (e.g. a per-thing sensory feature, or an order-sensitive observable like a labelled occupancy), or drop the `swap` condition from the change set and from the M3 report. Either way, delete the duplicate weighting.

## 12. The `tau=inf` "unique win" rests on a one-step margin, set by two arbitrary constants (serious for the interpretation)

**(1) Claim attacked.** "on a two-thing world with occlusion, tau=inf uniquely wins."

**(2) Why it fails.** The removal fires when `s["count"] > tau`, i.e. on the `(tau+1)`-th consecutive unconfirmed step. With `RUN_LENGTH = 9` and `CHANGE_STEP = 3`, a persistent occlusion (`occluded` is set once at t=3 and never cleared) gives at most 6 observes after the change, so a slot can accumulate at most `count = 6`. Therefore `tau=5` can only ever differ from `tau=inf` on sequences where a bound slot's thing is unseen at t=3,4,5,6,7,8 — and even then the difference is a single scored prediction (the t=9 one), because removal only happens at t=8. A `tau=6` would tie with `inf`; a run two steps shorter would let `tau=5` tie. The uniqueness is a property of the (run length, tau grid) pair, not clearly of the world. Note also that `tau=inf` retains slots whose thing has left the occluded region and whose velocity estimate has gone stale; on the one-thing world I argued in finding 4 that this cannot bite, but on the two-thing world the win may be partly "no removal path at all" rather than "object permanence".

**(3) Severity.** Serious for the word "uniquely"; the direction of the effect is probably right.

**(4) Fix.** Report the fitness gap between `tau=5` and `tau=inf` (not just the argmax), the distribution of maximum consecutive-unseen runs per change type, and extend the tau grid to include a value ≥ the run length (e.g. `tau=10`) so the reader can see the boundary. If `tau=10` also wins, the honest claim is "any persistence long enough to span the occlusion".

## 13. "Longest available prefix" is a misnomer and the key never falls back — and it hides the sequence's start (moderate)

**(1) Claim attacked.** `return tuple(self.buffer)  # longest available prefix, at most k fields`.

**(2) Why it fails.** `self.buffer` is a sliding window of the *most recent* `k` fields, not a prefix. Two consequences the design text should not paper over: (i) the lookup cannot see the initial configuration, which is precisely where the identity/velocity of the things is established; (ii) at long t it is the *hardest* key (length k) that is always used, with no fallback. The exposure table is built with the same key function, so the code is self-consistent, but the architecture is misdescribed.

**(3) Severity.** Moderate (mislabelling + the unfairness in finding 7).

**(4) Fix.** Rename to "last-k-fields key", and decide explicitly whether the design intends a prefix memoriser (then fix the implementation) or a fixed-order Markov model (then fix the label and add back-off).

---

## 14. The exposure/evaluation split is not stratified; for the one-thing world it is a cell/velocity checkerboard (moderate)

**(1) Claim attacked.** `"""Exposure half = even-index configurations; evaluation half = odd-index."""` used as a neutral held-out split.

**(2) Why it fails.** `states = [(c, v) for c in range(num_cells) for v in (-1, 0, 1)]` and `even = {tuple(c) for i, c in enumerate(confs) if i % 2 == 0}`. For `num_things=1` the index is `3c + (v+1)`; `i` even means `v+1 ≡ c (mod 2)`, so the exposure half receives `v = ±1` only on even cells and `v = 0` only on odd cells, and the complement for evaluation. The two halves are systematically different in the joint distribution of (position parity, speed), which is exactly what a k-gram table keys on. For `num_things=2` the parity depends on the `combinations_with_replacement` enumeration order, which is opaque. This is not a leak, but it is an uncontrolled split that can make the lookup's generalisation either artificially easy or artificially hard.

**(3) Severity.** Moderate.

**(4)** Report the composition of both halves (velocity histogram, boundary-adjacent counts) and use a stratified split, or use `i % 2` on a shuffled-but-fixed enumeration and report the seed.

## 15. The scored window includes a guaranteed-wrong step, which compresses all fitness differences (moderate)

**(1) Claim attacked.** `FIRST_SCORED_STEP = 2   # predictions for time points 2..9 are scored`, and the use of the aggregate fitness as the comparison statistic.

**(2) Why it fails.** `CHANGE_STEP = 3` applies the change *before* recording time point 3, so the prediction of time point 3 (issued from `seq[2]`) cannot be right for any deterministic function of the sensory prefix: the pre-change prefix is identical across change types for the same configuration. Every architecture, and the ceiling, eats that error, which deflates absolute fitness and the ratio-to-ceiling by a constant and hides architecture differences. There is no off-by-one in the window itself (I checked `evaluate`, `expose_lookup`, `sensory_ceiling` and `thing_signature`; indices `t+1` and `t ∈ range(RUN_LENGTH)` are consistent, `seq[t+1]` with `t+1 ≤ 9` is in range, and `range(CHANGE_STEP, RUN_LENGTH + 1)` covers t=3..9 as intended); the problem is *what* is inside it, not where it is.

**(3) Severity.** Moderate.

**(4) Fix.** Report per-predicted-time-point accuracy, or exclude the change-crossing prediction from the aggregate and report it separately as an un-predictable baseline.

## 16. The world's dynamics and the model's dynamics are the same function (serious overclaim about "emergence")

**(1) Claim attacked.** The framing that a thing-kind "emerges from selection".

**(2) Why it fails.** `step_kinematics` is called in `generate_sequence` for the world and again in `advance_slots` and `predict` for the slots. The hypothesis class therefore contains the ground truth *exactly*: a one-slot rule with the right velocity is a perfect predictor of an occluded thing, because the world and the model bounce off the same walls with the same formula. Given that, the selection result is close to analytic: the un-forgetting variant of a true-dynamics tracker must win whenever occlusion lasts longer than a competing `tau`. Nothing about "responsiveness to change" is being discovered.

**(3) Severity.** Serious for the interpretation, not for the code's correctness.

**(4) Fix.** Either state the claim much more weakly ("the grammar contains a perfect tracker and selection finds it"), or make the model's dynamics a distinct estimate (unknown reflection behaviour, a learned bounce rule) so that winning is informative.

---

## 17. The evolutionary secondary is a near-exhaustive search of a 208-point space (moderate — "blind search" overclaim)

**(1) Claim attacked.** "a blind mutation-selection search lands on the same architectures".

**(2) Why it fails.** `population_size=32, elite=4, generations=40` over `enumerate_architectures()` (208 architectures), with the top 4 copied verbatim into every generation and a shared deterministic `fitness_cache`. That is ≥ 1280 evaluations across a 208-point space with monotone elitism; hitting the global optimum is near-certain and tells you nothing about the structure of the fitness landscape. The "agreement" with the exhaustive selection is also the same statistic (finding 10).

**(3)** Moderate.

**(4)** Report the number of *distinct* architectures evaluated, and measure the search against a held-out confirmation fitness so that "lands on the same architecture" is not the same number as the selection criterion.

## 18. `thing_signature`'s `unbound` counter conflates three different failures, making architectures incomparable (moderate)

**(1) Claim attacked.** `"unbound_pairs": unbound` and `"fraction": passed / total` as a per-architecture score.

**(2) Why it fails.** `if not ok or len(binding) != len(things)` is reached both when the model has too few slots (`num_slots=1` in a two-thing world can never bind, so it reports `fraction = 0` with `unbound = total` by construction) and when the model is merely not tracking yet. Aggregate numbers across the M3 table therefore mix "cannot represent the situation" with "has not converged". Any statement of the form "architecture X passes 100%" needs the `num_slots ≥ num_things` qualifier, which the code does not attach.

**(3)** Moderate.

**(4)** Break `unbound` into `insufficient_slots`, `state_mismatch_at_bind_time`, and `tracking_lost`, and report the three separately.

## 19. Minor/cosmetic items

- The comment `"""Section 5 / section 8 step 2 of the design (as amended)"""` is unauditable from this file; if the design text says otherwise, the code is the only record of the amendment (cosmetic / moved-goalpost risk).
- `run_controls` rebuilds two histories and their splits that `main` already built (`h_neutral`, `h_full`), and its ceiling keys (`ceiling_H_neutral_evaluation_half`) are unused except for `H_full`; duplicated computation invites divergence (cosmetic).
- `results["protocol"] = "exposure on even-index configurations; every fitness is on the odd-index half"` is false for M3, which is run on `enumerate_configurations(6, 2)` — all configurations, including the exposure ones (minor accuracy of a claimed protocol).

## 20. Things I checked that did *not* turn up a bug (stated so you do not have to re-audit them)

- **Off-by-one in the scoring window:** none. `expose_lookup` (`t ∈ 0..8`, target `t+1`), `evaluate` (`t+1 ≥ FIRST_SCORED_STEP`), `sensory_ceiling` (same guard) and `thing_signature` (`range(CHANGE_STEP, RUN_LENGTH+1)`) are all mutually consistent with their docstrings.
- **Buffer/state leaking across sequences:** none. `reset()` clears `buffer`, `previous_field` and `slots`, and it is called per sequence in `expose_lookup`, per sequence in `evaluate`, and per change in `thing_signature`.
- **Exposure/evaluation table leak:** none. The table is only ever written from `exposure` and only read in `evaluate`; `split_history` keys on the whole configuration so a configuration never straddles the halves.
- **A "confirmed slot with a stale `count` gets deleted" bug:** not reachable. After every reconcile all surviving slots satisfy `count ≤ tau`, so a slot that is confirmed at the next reconcile cannot have `count > tau`. The `tau != "inf"` guard therefore does not by itself advantage `inf` through this path (the advantage comes from occlusion, finding 12).
