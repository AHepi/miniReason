# Authoring a Kimi K3 worker task

Ruling 16 makes kimi-k3 the default worker for mechanical and scripted work. This
page is what the five judge readings of the 26-task battery say about *writing the
task*, as opposed to reading the result. Every rule below cost a run.

## The eight rules

**1. `context_paths` must carry the module's own imports.** `b-02-seats` shipped
`seats.py` without `.types` and `.contracts`, which it imports at lines 102-103. The
worker could not import the module under test, wrote 49 tests that all skip, and the
project's own withheld suite failed in that sandbox identically. The task was not
winnable as declared. Before shipping a task, resolve the target's imports and copy
the siblings in — and check it: `python3 -c "import sys; sys.path.insert(0,'src');
import pkg.mod"` inside a copy of the sandbox must exit 0.

**2. `verify_command` is one `python3` invocation with no shell syntax.** The
allow-list is `python3 -m unittest …`, `python3 -m pytest …`, `python3 -c …`,
`python3 file.py …` — no pipes, no `&&`, no `;`, no redirects, no `cd`. Workers reach
for shell anyway (`> /tmp/c1.log 2>&1; echo "exit=$?"` in e-01, `&&` in e-04) and one
worker spent iterations 20-40 debugging an exit code its own `| tail -30` had
produced. Give the exact command in the prompt, in the form the allow-list accepts.

**3. List `expected_outputs`, as paths.** `COMPLETE` now means *the final turn
finished and every declared output exists*; a finished turn with nothing written is
`NO_DELIVERABLE`. That check only works if the outputs are declared as sandbox-relative
paths (`out/report.md`, `check/`). Prose entries like the smoke task's "a passing
unittest run" score nothing.

**4. The prompt names the output file, the script location, and says "do it by
computation".** The best runs in the battery generated their deliverable from a
checker they wrote (`check/f001_classify.py`, `check/occ02_usage.py`) and re-ran
byte-identically; the errors clustered in hand-written prose and in volunteered
extras nobody asked for. So: one output file, one script under `check/`, the report
generated by the script, and an instruction to re-run it before finishing.

**5. Keep the context small — the whole of it is re-sent every turn.** `d-02` spent
772,986 prompt tokens for 39,684 completion tokens over 14 iterations; `e-04` spent
1,262,135 for 44,523. That is the harness re-sending the sandbox context on every
turn, not the worker re-reading. Ship the two or three files the task actually needs,
not the directory that contains them. Family F, whose tasks write one script and run
it, is the only family that survived pass 1 intact — short turns on a small context
is the shape that works.

**6. Budget the turn, not the task.** `max_tokens` is per turn, and this model's
native reasoning is billed against it. At 8192 every reasoning-heavy turn in passes 2
and 3 returned empty (`RUNS-RECLASSIFIED.md`: 16 runs, all exactly 8192 completion
tokens, 28k-37k characters of reasoning, nothing written). The default is now
**24576**, which fits the observed reasoning with room for an answer and still lands
inside the 300 s gateway wall at ~90-100 tok/s. Do not raise it past ~25k: the wall
closes the connection mid-generation and the whole turn is lost.

**7. Leave `reasoning` at `"low"` and `transport` at `"native"`.** The loop now
speaks Ollama's `/api/chat`, which honours `think`: the smoke task ran four turns on
28, 0, 0, 0 characters of reasoning where `/v1` was spending 27k-37k *per turn*.
`"off"` (`think: false`) is for tasks that are pure mechanism; `"default"` sends no
control and is for a task you are deliberately letting think. `"transport": "v1"` is
there for a task that needs the OpenAI surface, and is also the automatic one-time
fallback if the native surface fails before any tool call.

**8. Iteration caps should be generous; they are not the binding constraint.**
Family D used 14 of 30, 7 of 20, 8 of 25. Where a cap did bind (`a-01`, `a-02`,
`a-03`, `b-02` at 40) the run had been thrashing for twenty turns. A cap of 30-40 is
right; if a task needs more, the task is too big.

## What does not go to Kimi

Anything needing `git`, a shell, or a network tool: `run_command` refuses all three,
and no amount of prompting changes it. Semantic argument over FW5, design decisions,
publication (push, ledger appends, publish-and-verify) and judging Kimi's own output
stay with Opus — a Kimi judge of Kimi is not independent.

## Before you dispatch

```bash
python3 -m unittest discover -s tests -t .          # 49 offline tests, no key needed
python3 run_battery.py --only <task-id> --workers 1 # one task
python3 run_battery.py --max-tokens 24576 --max-iterations 30
```

`result.json` also carries `reasoning_chars` (per turn), `transport_used` and
`transport_fallbacks`, and `SUMMARY.md` prints all three: per-turn reasoning length
is the number that tells you whether a task is about to lose a turn.

Then read `result.json`, not the console line: `status`, `expected_outputs_missing`
and `files_written` together are the delivery check. A `COMPLETE` with an empty
`files_written` is now impossible to record — but an `INCOMPLETE_TURN` still means
the turn was lost to reasoning, and the run should be re-dispatched with a smaller
context rather than a larger budget.
