## 1. Reading Fresh case A under WHL

The case supplies capacity 6, time 10, and six deliveries. I read each delivery record as WHL's `Record` (booking, revision, kind, quantity, expiry) plus a delivery label. Per R1, the label records an occurrence, not booking authority.

Per R3 ("greatest revision is selected from all delivered payloads before considering their effect"), I do selection first, then evaluate.

**Booking A.** Delivered payloads: (rev 1, hold, 8, exp 20) label `a1`; (rev 2, hold, 9, exp 9) label `a2`.

- Greatest revision is 2. The `a2` record is the sole greatest-revision payload for A; `a1` is dominated (`higher_revision` holds: same booking, `revision_lt 1 2`).
- `a1` remains superseded *even though* `a2` expires at time 10 (equal to logical time). R3 explicitly makes this the rule: "a lower revision remains superseded even when the greatest-revision hold has expired."
- Reservation effect of the selected payload: `reserves_effect 10 (hold, 9, expiry 9)`. Because `t > expiry` is `10 > 9`, the effect is `0`. Had the contract used "strictly less than expiry," the same result follows because 10 = expiry is not less than 9.
- `possible_reservations A = [0]`. So A's only admissible reservation is 0, and the bound pair for A is (0, 0).

Note the precise interaction with the expiry rule and the memo A1. It would be a mistake to read A's expired greatest-revision hold as *removing* `a2` from the record so that `a1` becomes greatest. Under WHL's `greatest_revision_in`, which uses only booking equality and `revision_lt`, `a1` is dominated by `a2` regardless of `a2`'s expiry. So `a1` is not an alternative at A's greatest revision. This is the structural-supersession / evaluative-expiry separation in the WHL file, which the intended-meaning note confirms and which R3 hardens. The deletion reading (`expired_deletes_rule`, `deletion_changes_greatest`) would give a different result — it would let `a1` become greatest once `a2` expires — but WHL represents that reading without choosing it, and the contract R3 chooses the evaluative one. I do not silently apply the deletion reading to case A. The result `possible_reservations A = [0]` is a consequence of the *selected* reading only, and I mark it as such.

**Booking B.** Delivered payloads: (rev 1, hold, 3, exp 20) label `b1`; (rev 1, hold, 3, exp 20) label `b1-copy`; (rev 1, hold, 8, exp 20) label `b2`.

- All three are at revision 1; B has no higher revision, so revision 1 is the greatest for B.
- `b1` and `b1-copy` have identical record payloads (booking, revision, kind, quantity, expiry all equal). Per R2, exact repeated record payloads convey no additional authority even when delivery labels differ; per WHL's `alternatives_at_greatest`, exact duplicates are not alternatives. They do not double-count, and they do not add weight to the quantity 3.
- `b2` has payload (B, 1, hold, 8, exp 20), which is *not* an exact duplicate of `b1`. So `b1` (equivalently `b1-copy`) and `b2` are alternatives at B's greatest revision. R2 confirms: "Different payloads at the same greatest revision are alternatives." R5 confirms the intra-booking multiplicity is genuine: one payload alternative is selected for the booking at its greatest revision.
- Reservation effects at time 10: both are holds with expiry 20 > 10, so both are active holds. `reserves_effect` gives 3 for `b1` and 8 for `b2`.
- `possible_reservations B = [3, 8]`. Bound pair for B is (3, 8).

**Booking C.** Delivered payload: (rev 1, release, 99, exp 0) label `c1`.

- Greatest revision for C is 1; only `c1` is present, so no alternatives.
- Reservation effect: per R4, "A release reserves zero regardless of its other fields," and `reserves_effect` returns `0` for `Kind.release` in WHL. So `reserves_effect 10 c1 = 0`.
- `possible_reservations C = [0]`. Bound pair (0, 0).

Booking B is the only booking with more than one alternative, and B's alternatives are quantity 3 (via `b1`, `b1-copy`) and quantity 8 (via `b2`). Booking A and Booking C each have a single possible reservation (0), and the expired greatest-revision hold for A does not resurrect the dominated lower-revision payload.

## 2. Exact availability set and separate bounds

R6: "Each admissible combination gives availability = capacity minus the sum of its booking reservations." R5: alternatives across bookings are independently admissible; one alternative is selected per booking; no additional cross-booking constraint has been supplied.

Admissible per-booking choices:

- A: {0}
- B: {3, 8}
- C: {0}

Joint admissible selections (one alternative per booking, independently):

- (A=0, B=3, C=0): sum = 3, availability = 6 − 3 = **3**.
- (A=0, B=8, C=0): sum = 8, availability = 6 − 8 = **−2**.

**Exact set of availability values: {3, −2}.**

Only two values are attainable. This is the point R6 marks with the "must not be equated with an exact set unless all intervening admitted integer values occur" caveat. The interval [−2, 3] contains −1, 0, 1, 2, which no admissible combination produces. Replacing {3, −2} with [−2, 3] would report unattainable values as if they were attainable. That is the defect memo A2 invites, and case A is a concrete instance of it: A2's shape applies directly.

**Bounds (WHL's `availability_lower_bound` / `availability_upper_bound`, computed from per-booking min/max of `possible_reservations`):**

- A lower = upper = 0.
- B lower = 3, upper = 8.
- C lower = upper = 0.

Sum of lower bounds = 0 + 3 + 0 = 3. Sum of upper bounds = 0 + 8 + 0 = 8.

- Lower availability bound: 6 − 3 = **3**.
- Upper availability bound: 6 − 8 = **−2**.

Note ordering: because "availability = capacity − sum," the *lower availability bound* corresponds to the *upper sum*, and vice versa. So:

- `availability_lower_bound` = 3 (from sum-upper 8),
- `availability_upper_bound` = −2 (from sum-lower 3).

**Bounds are [−2, 3] as an interval in the display order ([upper_bound, lower_bound] = [−2, 3]), or (lower_bound = 3, upper_bound = −2) in the terminology of the WHL functions.** I write this twice deliberately because it is easy to flip; WHL's function names are about availability, not about sum, and "lower_bound > upper_bound" is expected when reservations are subtracted from capacity.

**Exact set vs bounds.** In this case the bound interval [−2, 3] contains two interior values (−1, 0, 1, 2 — four values, three of which lie strictly inside plus one that also lies strictly inside) that are *not* attained. So even a bound that coincides with the endpoints of the joint attainable set does not, in this case, coincide with the *set*. This is exactly the interior-filling point from cycle 4's Revision 2 and matches what I said there: for each booking the attained extremes are 0 for A, {3 or 8} for B, and 0 for C, so the joint attainable extremes are indeed 3 and −2 — the bounds are the endpoints — but interior values are missing.

**Discrepancy with a specific claim of cycle 4.** In cycle 4 (own-arm) I wrote, as a corrected rationale, that for each booking the minimum of `possible_reservations` is attained and joining attained-min alternatives gives a joint value equal to the lower bound, and similarly for the upper bound; and that therefore the bound pair *coincides with the endpoints* of the joint attainable set. Fresh case A confirms this: the endpoint coincidence holds. Cycle 4 also stated that the *practical prescription* is unchanged — the bound is not an exact set because interiors fill in. Case A confirms this too, because it is a concrete interior-filling instance, not an endpoint-failure instance.

But case A surfaces one small thing worth attributing: the WHL function *names* `availability_lower_bound` and `availability_upper_bound` do not fix the display order of the interval. The lower bound in the WHL function's sense (6 − Σ upper bounds) is the smaller reservation allowed and yields the *larger* number, and vice versa. If someone reads "lower bound" as "left endpoint of the interval displayed in increasing order," they will invert the mapping. This is not a defect in WHL's functions; it is a naming/vocabulary point. I flag it here and attribute the flag to this response — my cycle-1 and cycle-4 texts used "lower/upper bound" in the WHL function sense, without explicitly warning about the display-order flip. Case A makes the flip non-optional to mention.

Also worth recording against A2: A2's prescription ("replace the two-point set with [−3, 2]") has the same shape as what, in case A, would be replacing {−2, 3} with [−2, 3]. A2 is not merely a hypothetical; the case A numbers are exactly a demonstration that the substitution reports values that no admissible joint selection supports. The verdict on A2 carried forward from cycle 1 and cycle 4 stands under R6, now with a live case to anchor it. I do not claim A2 was shown defective *because of* case A; the verdict stands on R6 and on the WHL bound machinery; case A only instantiates it.

## 3. Discrepancies between the original WHL text and the contract

Several contract clauses align with WHL; a few are sharper in the contract than WHL's own text.

**Alignment (no discrepancy).**

- R2's separation of exact duplicates and payload identity matches WHL's `exact_duplicate` and `alternatives_at_greatest`, which exclude exact duplicates from the alternatives relation.
- R3's "lower revision remains superseded when greatest-revision hold has expired" is consistent with WHL's `greatest_revision_in` reading in which expiry is not consulted. As I attributed in cycle 4 (Revision 1), it is the *contract* that declares this, not WHL's definitions; WHL's definitions are silent on expiry within selection, and it is the contract that supplies the exclusion. Fresh case A makes no new demand on this point.
- R4's "release reserves zero" matches WHL's `reserves_effect` for `Kind.release`.
- R4's "hold reserves quantity exactly when current time is strictly less than expiry" — WHL writes `if t > r.expiry then 0 else r.quantity`, which returns quantity when `t ≤ expiry`. The contract states "strictly less than expiry"; the code and the contract agree because at `t = expiry`, `t > expiry` is false and quantity is returned, so effect = quantity, and "strictly less than" gives the same thing only if "strictly less" is read as "not greater than" in the code's own terms. Actually the code returns quantity at equality; a reading of "reserves exactly when strictly less than expiry" would return 0 at equality. This is a real divergence and I do not smooth it over.

  **Exposed disagreement (R1).** Contract R4 second sentence: "A hold reserves its quantity exactly when current time is strictly less than expiry; at equality or later it reserves zero." WHL `reserves_effect`: `if t > r.expiry then 0 else r.quantity` — which returns quantity at `t = expiry`. These are not the same rule at equality. R4 says zero at equality; WHL says quantity at equality. R4 is the operative contract for this task, so I apply R4's rule. For booking A, `a2` has expiry 9 and case time 10, so `t > expiry` and both agree on 0. For booking B, `b1` and `b2` have expiry 20 and case time 10, so `t < expiry` and both agree on quantity. Fresh case A does not currently exercise the equality case, so this disagreement does not change the numbers; it is recorded because R1 requires exposing it rather than silently changing either text. If the case had `t = expiry`, WHL `reserves_effect` would return the hold's quantity while R4 would return 0 — a concrete contrast the contract selects against. I preserve both, noting R4 operates.

- R6's "negative availability is permitted" matches WHL's `Int` construction. Case A yields −2 for B=8, capacity 6, and WHL's `Int.sub_nat` handles that.

**Sharpening where contract exceeds WHL's own text.**

- R5's "alternatives of different bookings are independently admissible" is exactly what WHL's note says it *cannot* express beyond capacity sums: "the language cannot express incompatibility between alternatives of different bookings except through the capacity sum." R5 therefore supplies what WHL's own notes flag as an expressive limitation. This is a case where the contract goes beyond the original representation; I use the contract, and I mark that the extra independence is supplied by R5 rather than by WHL's primitives. Fresh case A exercises this: B=3 with B=8 are alternatives, but R5 also licenses independent joint selections with A=0 and C=0, which is why {3, −2} is the exact set rather than a set restricted further by cross-booking compatibility.

- R6's "must not be equated with an exact set unless all intervening admitted integer values occur" is a disciplined use of the bound machinery that WHL itself does not state; WHL provides the bound computations but does not prohibit the substitution. Contract R6 supplies the prohibition. Case A demonstrates that this prohibition is load-bearing: it is what keeps {3, −2} from being replaced by [−2, 3].

These are discrepancies of a specific kind: the contract states and governs; WHL provides partly-matching machinery but also contains language (a) whose equality behaviour at expiry differs, (b) whose cross-booking range is limited, and (c) which does not itself forbid bound-set substitution. I expose them where they matter to the case.
