## 3. The new problem in the task: which kind, and what must be supplied

The task's operative new problem is memo B's *cross-booking coupling*: "Rejecting the rule that bookings are independent opens a legitimate question about the missing coupling policy. The old result under the originally specified independent-choice task remains a distinct conditional claim."

**Kind.** It is a **scope-open** question, not an expressive-open one. Distinction, attributed to this response (partly drawn already in cycle 8 §5):

- *Expressive-open*: WHL's language cannot represent the missing coupling at all, so a *language extension* would be required. WHL's own notes say the language cannot express incompatibility between alternatives of different bookings "except through the capacity sum". This is a stated expressive limitation.
- *Scope-open*: R5 *supplies* per-booking independence as a specified task scope and explicitly calls this "a specified task scope, not a universal claim about physical warehouses". The independence could be withdrawn or widened by a contract revision or a case stipulation without language extension.

B6's question is scope-open. R5's own scope sentence and WHL's expressive-limitation note both license *reopening* the question; neither forces a language extension to do so. Conflating the two would invite the very "manufactured policy" the task warns against.

**What would have to be supplied to investigate it without manufacturing a policy.** Cycle 6 gave three prerequisites; I retain them, sharpen one, and add a fourth.

1. **What couples the bookings.** A statement of which physical resource other than aggregate capacity is shared, or which pairing of alternatives (across bookings) is incompatible. WHL's `Snapshot` has only `capacity` as a global constraint; any coupling must therefore be supplied from outside the current `Snapshot`.
2. **Whether the coupling is a restriction on *selections* or a reinterpretation of *what counts as live*.** WHL's types separate `ReservationRule` (a function `Time → Record → Quantity`) from the per-booking alternative structure produced by `possible_reservations`. A coupling that restricts *joint* selections across bookings is neither: it operates on the product of per-booking alternatives, which WHL's current `possible_reservations : Snapshot → Booking → List Quantity` does not carry. Naming which of these is being proposed is required before any computation.
3. **Whether the coupling is a *case assumption* or a *proposed language extension*.** If case assumption, it can be stated as a supplied stipulation applied to the current representational vocabulary. If language extension, it must be declared as an extension to WHL and attributed. This distinction does not exist in WHL's primitives directly (it is the R8 register of "proposed or disputed"), but it is exactly what the task demands.
4. *(added here)* **Whether the coupling changes the availability *set*, the *bounds*, or only which *endpoints* are acceptable.** R6 makes "an interval may be reported as bounds but must not be equated with an exact set unless all intervening admitted integer values occur" a hard constraint. A coupling that removes or adds admissible joint selections can collapse the interval onto the exact set, or push the set outside the old interval. The supply must state which, because "the old result remains a conditional" (B6's second sentence) is protectible only if the coupling's effect is characterised *before* it is applied.

Absent (1)–(4), I do not compute a coupled result. Cycle 9 records the prerequisites and leaves the coupling question open, per the task's own instruction not to manufacture a policy.
