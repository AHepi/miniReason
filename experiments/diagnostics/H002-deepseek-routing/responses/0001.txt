## Chosen interpretation of the proposed update rules

I read the candidate's §4 rules as follows, applying them literally but coherently:

- §4.1/§4.2 (L insert/delete) affect only the touched `lid`: remove all currently-emitted triples for that `lid` and, if it survives, re-emit according to the new key. `LkeyIndex` and `Lrows` are mutated; `Rrows`/`RkeyIndex` are not.
- §4.3/§4.4 (R insert/delete) affect exactly the left rows whose key equals the right row's non-NULL key. The NULL key case (`R.k IS NULL`) touches only `Rrows` and leaves output unchanged, because ordinary `=` is never true with a NULL operand. On the non-NULL case, every left row `x ∈ LkeyIndex[k]` loses/regains its NULL branch according to whether the matching set of right rows goes `0→1` or `1→0`.
- Multiplicity is preserved by treating `RkeyIndex` buckets as multisets (bags) of `rid` — distinct `rid`s under the same `(k,v)` produce duplicate output triples.
- The candidate does **not** retain `matchCount`; cardinality `cnt(k) = |RkeyIndex[k]|` is derived on demand from the bucket. I honor that: I will not store `matchCount`.
- Whole-row before-images supplied in the event (`[lid,k]` for L, `[rid,k,v]` for R) are used as the authoritative deletion target, and the retained state is expected to agree with them.

## Missing / inferred rule I must supply

The candidate's §4.2 and §4.4 describe the delta in terms of `cnt(k)` and the matching right rows, but they do not spell out the bookkeeping when the **whole non-NULL bucket empties**. To apply §4.4 literally for `R.rid = 10` with `k = 7`:

- I must compute `cnt(7)` *before* removal and detect the `1→0` transition across all affected left rows. Here `cnt(7) = 2`, so no transition.
- I must remove exactly one occurrence of `(x.lid, 7, 'a')` from the cached output bag for each `x ∈ LkeyIndex[7] = {2}`. "One occurrence" is the inferred rule: with duplicates, the removal is by count, not by value identity. This is consistent with the candidate's multiset semantics and is what I use.
- I must then remove `rid = 10` from the `RkeyIndex[7]` bucket and from `Rrows`, dropping the bucket only if it empties (it does not).

I record this as an **inferred rule**: deltas on the output bag are single-occurrence multiset operations, never set operations. The candidate flagged (§7 item 3) that this distinction is under-specified in prose; I adopt bag removal here.

3. **No whole-database recomputation** was used; only retained state and the next event, per contract.
4. **No SQL executive was invoked.** The output bag above follows the candidate's closed form and update rules as interpreted, not a fresh scan of `L`/`R`. If the SQLite execution of the same event sequence diverged from this bag, the divergence would be evidence against the candidate's or my inferred rule, not against the retained-state construction's internal consistency.
