## Event 1 — `insert L [1, 7]`

**Rule:** §4.1. `lid=1` absent; `k=7` non-NULL.

**Affected keys:** key 7 only, and only via the new left row. Right side unchanged; no other left row's branch can change (branches depend on each row's own key and on `RkeyIndex`).

**Branch decision:** `cnt(7) = |RkeyIndex[7]| = |[11]| = 1`, so this is the **match branch**, not the NULL branch.

**Output delta:** for each matching right row in `RkeyIndex[7]` = `[11]` with value `"a"`, add `(1, 7, "a")`. One addition.

**State mutations:**
- `Lrows` += `[1,7]`
- `LkeyIndex[7]` = `[2]` → `[2,1]` (order immaterial)

**Unchanged:** `Rrows`, `RkeyIndex`; key-9 bucket, index and output entry all untouched.

}

## Event 2 — `delete R [11, 7, "a"]`

**Rule:** §4.4. Before-image matches live `Rrows` entry; `k=7` non-NULL.

**Affected keys:** key 7 only. `LkeyIndex[7] = [2,1]`. Right row `rid=11` is the sole surviving member of `RkeyIndex[7]`.

**Transition test:** `cnt(7) = |[11]| = 1`; `willBeEmpty = (cnt(7) == 1) = true`. This is the 1→0 transition.

**Output delta per affected left row `x ∈ {2,1}`:**
- remove one occurrence of `(x, 7, "a")`, add `(x, 7, null)` (NULL branch swap).

So: remove `(2,7,"a")` and add `(2,7,null)`; remove `(1,7,"a")` and add `(1,7,null)`.

**State mutations:**
- Remove `rid=11` from `RkeyIndex[7]` → bucket empties → drop bucket. `RkeyIndex` now only has key 9.
- Remove `[11,7,"a"]` from `Rrows`.

**Unchanged:** key-9 rows, index, and output entry; `LkeyIndex`.

### Retained state after Event 2
```json
{
  "Lrows":    [[2,7],[3,9],[1,7]],
  "Rrows":    [[12,9,null]],
  "LkeyIndex":[[7,[2,1]],[9,[3]]],
  "RkeyIndex":[[9,[12]]]
}
```

### Output bag after Event 2
```
[[2,7,null], [3,9,null], [1,7,null]]
```

| lid | k | v |
|-----|---|---|
| 2 | 7 | NULL  (no-match branch) |
| 3 | 9 | NULL  (matched value) |
| 1 | 7 | NULL  (no-match branch) |

**Note the two distinct NULLs now coexisting in column `v`:** lid 2 and lid 1 are on the **no-match branch**, while lid 3 is on the **match branch** whose matched `v` happens to be SQL NULL. Output shapes look identical; provenance differs. This distinction is retained in state, not in the bag.

## Event 3 — `insert R [13, 7, null]`

**Rule:** §4.3. `rid=13` absent; `k=7` non-NULL (the *key* is 7; the *value* is NULL).

**Affected keys:** key 7 only, via `LkeyIndex[7] = [2,1]`. Key 9 untouched — no left row with key 9 is walked, and no right row with key 9 is involved.

**State of bucket before insert:** `RkeyIndex[7]` is **absent/empty** (dropped at Event 2). So `wasEmpty = true`. This is the 0→1 transition.

**Output delta per affected left row `x ∈ {2,1}`:**
- remove the NULL-branch triple `(x, 7, null)`, add the match triple `(x, 7, null)`.

The two triples are **textually identical**, so at the bag level the delta is net zero. Concretely: `(2,7,null)` is removed and `(2,7,null)` is added — the bag is unchanged in content and multiplicity for lid 2. Same for lid 1. **However**, the *provenance* of each surviving `(x,7,null)` changes from no-match-branch to match-branch, and that change must be reflected in state (see mutations), even though the bag itself does not move.

**State mutations:**
- Create `RkeyIndex[7] = [13]`.
- `Rrows` += `[13,7,null]`.

**Unchanged:** `Lrows`, `LkeyIndex`; key-9 bucket, index, and output entry.

### Retained state after Event 3
```json
{
  "Lrows":    [[2,7],[3,9],[1,7]],
  "Rrows":    [[12,9,null],[13,7,null]],
  "LkeyIndex":[[7,[2,1]],[9,[3]]],
  "RkeyIndex":[[7,[13]],[9,[12]]]
}
```

### Output bag after Event 3
```
[[2,7,null], [3,9,null], [1,7,null]]
```

| lid | k | v |
|-----|---|---|
| 2 | 7 | NULL  (now match branch, `rid=13`) |
| 3 | 9 | NULL  (matched value) |
| 1 | 7 | NULL  (now match branch, `rid=13`) |

**Projected multiplicity note:** the three output rows remain a multiset of three, in the same textual shape as after Event 2. Only provenance and the internal branch classification changed. This is the event where a purely bag-textual invariant would mislead: the bag is agnostic to NULL-branch vs matched-NULL here.

## Event 4 — `insert R [14, 7, "c"]`

**Rule:** §4.3. `rid=14` absent; `k=7` non-NULL.

**Affected keys:** key 7 via `LkeyIndex[7] = [2,1]`. Key 9 untouched.

**Bucket state before insert:** `RkeyIndex[7] = [13]`, so `cnt(7) = 1`, `wasEmpty = false`.

**Output delta per affected left row `x ∈ {2,1}`:**
- `(x, 7, "c")` added, once per row. No NULL-branch swap.

So: add `(2,7,"c")`; add `(1,7,"c")`.

**State mutations:**
- `RkeyIndex[7]` = `[13]` → `[13,14]`.
- `Rrows` += `[14,7,"c"]`.

**Unchanged:** `Lrows`, `LkeyIndex`; key-9 bucket, index, and output entry.

### Retained state after Event 4
```json
{
  "Lrows":    [[2,7],[3,9],[1,7]],
  "Rrows":    [[12,9,null],[13,7,null],[14,7,"c"]],
  "LkeyIndex":[[7,[2,1]],[9,[3]]],
  "RkeyIndex":[[7,[13,14]],[9,[12]]]
}
```

### Output bag after Event 4
```
[[2,7,null], [3,9,null], [1,7,null], [2,7,"c"], [1,7,"c"]]
```

| lid | k | v |
|-----|---|---|
| 2 | 7 | NULL  (matched `v` of `rid=13`) |
| 3 | 9 | NULL  (matched `v` of `rid=12`) |
| 1 | 7 | NULL  (matched `v` of `rid=13`) |
| 2 | 7 | "c"   (matched `v` of `rid=14`) |
| 1 | 7 | "c"   (matched `v` of `rid=14`) |

**Projected multiplicity:** lid 2 now emits **two** rows (one per matched right row of key 7); lid 1 likewise. Lid 3 emits one. Bag size 5, matching `|Lrows with key 7|·|RkeyIndex[7]| + |Lrows with key 9|·|RkeyIndex[9]|` = `2·2 + 1·1 = 5`. Both `L` rows with key 7 are on the **match branch** because `cnt(7)=2>0`.

## What happens to unaffected keys — specifically key 9

Across all four events, **key 9 is never the affected key**. No event inserts or deletes an `L` or `R` row with `k=9`. Under §4.3/§4.4, the only left rows walked are those in `LkeyIndex[affected k]`, and the only right bucket consulted is `RkeyIndex[affected k]`. Therefore:

- `LkeyIndex[9] = [3]` — never modified.
- `RkeyIndex[9] = [12]` — never modified.
- `Rrows` retains `[12,9,null]` throughout.
- The output row `(3,9,null)` — a **match-branch** row whose matched value happens to be NULL — is **never added, removed, or touched** by any of Events 1–4. It persists with multiplicity one from Event 1 through Event 4.

This is the concrete content of U1's rule "R insert/delete affect exactly `LkeyIndex[k]` for the right row's non-NULL key `k`." Key 9 never equals 7, so key-9 output is invariant across the batch.

**Comparison with Event-3-style no-match NULLs for key 9:** had key 9 *ever* been affected via an R-bucket transition, the `(3,9,null)` row would potentially swap between no-match-branch and match-branch provenance. That never happened here.
