# Retained-state account for maintaining `SELECT ALL L.lid, L.k, R.v FROM L LEFT JOIN R ON L.k = R.k`

## 1. What the target output is

For current tables `L` and `R`, the output bag is

\[
Q \;=\; \biguplus_{\ell \in L}\;\bigl\{\,(\ell.\mathrm{lid},\ \ell.k,\ r.v)\ \big|\ r \in R \text{ and } \ell.k = r.k \,\bigr\}
\ \uplus\
\biguplus_{\ell \in L,\ \nexists r \in R: \ell.k = r.k}
\bigl\{(\ell.\mathrm{lid},\ \ell.k,\ \mathrm{NULL})\bigr\}.
\]

Two facts drive all maintenance:

1. **Every L row contributes at least one output row.** A match against zero or more R rows contributes one row per matching R row; a match against no R row contributes exactly one NULL-`v` row.
2. **R rows never contribute output except through an L row with an equal key.** An unmatched R row contributes nothing, but it can become visible when an L row with that key is inserted, or when a previously shadowed R row is revealed by operations that do not themselves touch R.

Because the join condition is ordinary SQL equality, NULL keys never match: if `L.k` is NULL, that L row always takes the NULL-`v` branch regardless of how many R rows with NULL `k` exist, and an R row with NULL `k` never matches any L row.

`SELECT ALL` means the bag of rows above is the answer, including duplicate `[lid,k,v]` triples when multiple R rows share a key that some L row has. Order is immaterial.

## 2. Retained state

The incremental contract has no post-initial database access, so the state must be sufficient to decide, for any incoming event, exactly which output rows appear and disappear.

### 2.1 State retained from `L`

For each lid present in `L`, retain:

- \(k_L(\mathrm{lid})\): its key, an integer or NULL.
- \(m_L(\mathrm{lid})\): the current multiplicity, i.e. the number of R rows whose key equals `k_L(lid)` when `k_L(lid)` is non-NULL, and necessarily \(0\) when `k_L(lid)` is NULL.

The lid set itself is part of state: retain the set \(\mathrm{Dom}(L) = \{\mathrm{lid} : (k_L,m_L)(\mathrm{lid})\text{ is defined}\}\). Because lids are unique, this is a partial map, not a multiset.

Note that \(m_L(\mathrm{lid})\) already encodes the join result for that L row under the current `R`: if \(m_L(\mathrm{lid})=0\), the L row is on the NULL branch; if \(m_L(\mathrm{lid})=t>0\), the L row currently contributes \(t\) rows, and their `v` values must be recoverable (see §2.2).

### 2.2 State retained from `R`

For each key value actually appearing in `R` (non-NULL only, since NULL keys cannot match), retain the **bag of `v` values currently attached to that key**:

\[
V_R(k) \;=\; \{\!\!\{ v \mid (r.\mathrm{rid}, k, v) \in R \}\!\!\}, \qquad k \in \mathbb{Z}\setminus\{\mathrm{NULL}\}.
\]

Only keys with \(V_R(k) \neq \emptyset\) need be stored. This is exactly the information that the output needs from `R`, because:

- the `v` values printed for a matched L row with key \(k\) are precisely the elements of \(V_R(k)\);
- the count \(m_L(\mathrm{lid})\) is \(|V_R(k_L(\mathrm{lid}))|\) whenever the key is non-NULL;
- R `rid`s never appear in the output, so they need not be retained beyond ensuring each delete's before-image names an existing row.

Retaining the full bag `V_R(k)` (rather than only its count) is necessary because the output includes the `v` values themselves, and because a deletion from `R` must know *which* `v` to remove. Retaining counts alone would suffice only if the output printed no `v` and if delete events carried the `v` as part of their before-image and we could not be asked to enumerate remaining rows.

### 2.3 Derived indexing retained for efficiency

To update `V_R` by key, retain a map \(K_R: \mathbb{Z}_{\neq\mathrm{NULL}} \to V_R(k)\). To update `m_L` for every affected L row on an R change, retain an inverse index

\[
\mathrm{LidsForKey}(k) \;=\; \{\, \mathrm{lid} : k_L(\mathrm{lid}) = k \,\}, \qquad k \in \mathbb{Z}_{\neq\mathrm{NULL}},
\]

i.e. the set of L row-ids whose key equals \(k\). This is required to avoid scanning all of `L` when `R` changes, and it is derivable from \(\mathrm{Dom}(L)\) and \(k_L\).

State is therefore a triple of maps:

\[
S \;=\; \bigl(\, L_{\text{state}}:\ \mathrm{lid} \mapsto (k, m),\quad
V_R:\ \mathbb{Z}_{\neq\mathrm{NULL}} \to \text{bag of }v,\quad
\mathrm{LidsForKey}:\ \mathbb{Z}_{\neq\mathrm{NULL}} \to \text{set of lid} \,\bigr).
\]

The map \(L_{\text{state}}\) is the authoritative source of \(\mathrm{Dom}(L)\) and \(k_L\); \(\mathrm{LidsForKey}\) is its key-projection.

### 2.4 What is *not* retained and why it is unused

- R `rid`s: never appear in the output and never affect the bag; each delete's before-image includes the rid, but the update needs only the key and the `v` from that before-image.
- The full R table outside `V_R`: unmatched keys and unmatched R rows carry no output relevance until an L row arrives, at which point only the key's `v` bag matters. Preserving `V_R(k)` for keys currently with no L row is *necessary* — otherwise inserting a matching L row later would compute the wrong output. So we keep \(V_R(k)\) for all keys in `R`, not only keys in `L`.
- L rows' history: only current \(k_L\) and current \(m_L\).
- No retained data about the output bag itself: every output change is recomputable from the state plus the event, and storing the output would be redundant (though permissible).

### 2.5 Connection from state to output

For any lid in \(\mathrm{Dom}(L)\) with key `k` and multiplicity `m`:

- if `k` is NULL or `m = 0`, the L row contributes exactly one output row `(lid, k, NULL)`;
- otherwise it contributes the \(|V_R(k)| = m\) rows `(lid, k, v)` for each `v` in `V_R(k)`.

The full output bag at any time is the disjoint union, over `lid \in \mathrm{Dom}(L)`, of these contributions. Disjointness is by lid, so multiplicities add without interference.

## 3. Initialization

Given read access to `L` and `R`, build state once:

1. For each `(lid, k)` in `L`: set \(L_{\text{state}}(\mathrm{lid}) \leftarrow (k, 0)\) and, if `k` is non-NULL, add `lid` to \(\mathrm{LidsForKey}(k)\).
2. For each `(rid, k, v)` in `R`: if `k` is non-NULL, append `v` to \(V_R(k)\).
3. For each `k` with non-empty \(V_R(k)\), for each `lid` in \(\mathrm{LidsForKey}(k)\), set \(m_L(\mathrm{lid}) \leftarrow |V_R(k)|\).

After this point the database is unavailable; the state above is the working memory. Initialization may also emit the initial output as the union in §2.5, if needed; that emission is not part of the retained state.

No other information is needed. In particular we do **not** need to record which `(lid,v)` output rows currently exist, because they are derivable.

## 4. Update rules

Throughout, "emit"/"retract" mean additions/removals to/from the output bag, itemized per affected lid.

For notation, define

\[
\Delta_{\text{emit}}(\mathrm{lid}, k, v) \;=\; \text{one output row }(\mathrm{lid},k,v)\text{ added},
\]
\[
\Delta_{\text{retract}}(\mathrm{lid}, k, v) \;=\; \text{one output row }(\mathrm{lid},k,v)\text{ removed}.
\]

Each event also updates state **before or alongside** producing output deltas, so that the state always reflects the post-event database.

---

### 4.1 Insert into `L`: event `(lid, k)`, lid currently absent

Precondition: `lid ∉ Dom(L)`. (If present, the event is illegal under the event definition; see §6.)

State change:

- If `k` is NULL:
  - \(L_{\text{state}}(\mathrm{lid}) \leftarrow (\mathrm{NULL}, 0)\);
  - no index update (NULL keys are not indexed by key);
  - output delta: emit \((\mathrm{lid}, \mathrm{NULL}, \mathrm{NULL})\).
- If `k` is a non-NULL integer:
  - \(t \leftarrow |V_R(k)|\) (0 if `k ∉ K_R`);
  - \(L_{\text{state}}(\mathrm{lid}) \leftarrow (k, t)\);
  - add `lid` to \(\mathrm{LidsForKey}(k)\);
  - output delta:
    - if \(t = 0\): emit \((\mathrm{lid}, k, \mathrm{NULL})\);
    - else: for each \(v \in V_R(k)\) (bag), emit one \((\mathrm{lid}, k, v)\).

This is the only place where the bag structure of \(V_R(k)\) (not just its size) is used by an L-side event, and it is used exactly to enumerate the newly visible output rows.

---

### 4.2 Delete from `L`: event is full before-image `(lid, k)`

Precondition: `lid ∈ Dom(L)` and \(k_L(\mathrm{lid}) = k\). (If not, the event is inconsistent with state; see §6.)

State change:

- Let \(m \leftarrow m_L(\mathrm{lid})\).
- If `k` is non-NULL:
  - remove `lid` from \(\mathrm{LidsForKey}(k)\);
  - (the `V_R(k)` bag is untouched by an L delete);
  - output delta:
    - if \(m = 0\): retract \((\mathrm{lid}, k, \mathrm{NULL})\);
    - else: for each \(v \in V_R(k)\) (current bag), retract one \((\mathrm{lid}, k, v)\). Note \(m = |V_R(k)|\) at this moment.
- If `k` is NULL:
  - output delta: retract \((\mathrm{lid}, \mathrm{NULL}, \mathrm{NULL})\).
- Remove \(\mathrm{lid}\) from \(L_{\text{state}}\).

Deletion of an L row is purely a removal of that lid's contribution. Other L rows are unaffected because the key index for R is unchanged.

---

### 4.3 Insert into `R`: event `(rid, k, v)`, rid currently absent

Precondition: `rid ∉ Dom(R)` as tracked by the retained evidence (§5). The event's contribution to state:

- If `k` is NULL:
  - no state change to \(V_R\) or any \(m_L\), because NULL keys never match;
  - no output delta.
- If `k` is a non-NULL integer:
  - append `v` to \(V_R(k)\);
  - for each `lid \in \mathrm{LidsForKey}(k)`:
    - increment \(m_L(\mathrm{lid})\) by 1;
    - emit \((\mathrm{lid}, k, v)\).

The last step adds one output row per L row that has key `k`, since the new R row is now visible to each of them. If `LidsForKey(k)` is empty, the R row is stored silently for possible future L insertions.

---

### 4.4 Delete from `R`: event is full before-image `(rid, k, v)`

Precondition: `rid ∈ Dom(R)`, and the retained bag for `k` contains a matching `v` (bag multiplicity ≥ 1); this is checked against state (§5).

- If `k` is NULL:
  - output delta: none.
  - No `V_R` or `m_L` change, since NULL keys are not stored.
- If `k` is a non-NULL integer:
  - remove one occurrence of `v` from \(V_R(k)\);
  - for each `lid \in \mathrm{LidsForKey}(k)`:
    - decrement \(m_L(\mathrm{lid})\) by 1;
    - retract \((\mathrm{lid}, k, v)\).
  - If \(V_R(k)\) becomes empty, delete the key from \(K_R\) (the empty bag need not be stored; on a later L insert, the key is simply absent and treated as count 0).

Every L row with that key loses exactly the row `(lid,k,v)`. If several R rows shared the same `v`, only one occurrence is removed; the choice of which rid is immaterial to the output bag, which is why rid is not retained.

---

### 4.5 A composed update event

The task defines updates as delete followed by insert. Applying §4.2 or §4.4 then §4.1 or §4.3, in that order, yields the composed effect. No special rule is needed. If the delete and insert have the same key (as in typical "modify `v`" events), the intervening state change may make the pre-delete and post-insert outputs differ in intermediate form; that is exactly the sequence the contract asks to observe event-by-event.

When a delete from `R` and an insert into `R` share the same key and the same `v`, the net state is unchanged and the per-event deltas cancel; the account still emits and retracts in strict event order, which matches the observation contract.

## 5. Checking event preconditions against state

The contract says deletes carry the full before-image and that the deletion "removes that id exactly once", and inserts must use an absent id. The retained state can verify the parts it observes:

- Inserts into `L`: `lid ∉ Dom(L)` is directly checkable. Because lids are unique in `L`, this fully verifies the insert.
- Inserts into `R`: whether `rid` is absent is *not* directly checkable from state, because `rid`s are deliberately not retained. What is checkable is that the key effect is consistent with the events contract: if the interpreter receives an `R` insert whose `rid` is actually a duplicate, the event is illegal, and the account cannot detect this from state alone. This is a residual limitation (see §6), not a silent repair.
- Deletes from `L`: `lid ∈ Dom(L)` and \(k_L(\mathrm{lid})\) equal to the before-image `k` are checkable.
- Deletes from `R`: whether `rid` was present is not directly checkable, but whether the bag \(V_R(k)\) contains the stated `v` is. If `k` is non-NULL and `v` is not in \(V_R(k)\), the event is inconsistent with state and must be rejected or flagged, not applied.
  - If `k` is NULL, the before-image carries no state signal at all, because NULL-key R rows are not retained. An "R delete with NULL k" event is therefore unverifiable beyond the fact that it is legal by the event contract; the account would apply it with zero output effect and zero state effect regardless of whether such a row actually existed. This is a genuine state-insufficiency for legality checking (though not for output correctness: if a NULL-key R row exists, deleting it cannot change output; if it does not exist, the event is illegal per the event contract, but the output is the same).

## 6. Unsupported cases and uncertainty

1. **NULL-key R rows carry no retained trace.** They never match and never contribute output, so `V_R(NULL)` is not kept. As a consequence:
   - the state cannot confirm or deny the existence of a specific NULL-key R row on delete, and cannot enumerate them;
   - two R tables that differ only in their NULL-key rows induce identical state and identical outputs, so output correctness is unaffected. This is an intentional insufficiency for legality checking, not for query maintenance.

2. **R `rid` identity is not retained.** As with NULL keys, this is an insufficiency for legality checking of R deletes and inserts (a duplicate insert cannot be detected; a delete of a *different* rid sharing the same `(k,v)` cannot be distinguished from the actual row). The output bag stays correct because rid is not part of the output and because the output's dependence on R is only through `(k,v)` multiplicity.

3. **Bag-of-values ambiguity in R deletes.** When several R rows share the same non-NULL key and the same `v`, the before-image `(rid, k, v)` doesn't determine which rid was meant from state alone; the account removes one occurrence of `v` and retracts one corresponding output row per matching L row. The output bag is correct; the retained state cannot confirm the rid was the one that existed.

4. **Event ordering and intermediate observations.** The account treats each event atomically and emits/retracts per event, which matches "after each event, the output is the complete bag". An update expressed as delete-then-insert therefore produces two observable intermediate outputs. No stronger guarantee is claimed.

5. **Whole-database recomputation.** Allowed only as an explicit alternative. It lies outside the incremental-use contract: recomputing `Q` from `L` and `R` after each event would bypass the retained state, but is not what this account proposes.

6. **No pre-supplied rules were assumed.** The rules in §4 were derived from the query semantics and the value-domain restrictions (integer/NULL keys, text/NULL values, integer lids/rids). If the value domain were extended (e.g. keys that compare non-reflexively, or collation-dependent equality), the "key" of `LidsForKey` and `V_R` would need to be the comparison-equivalence class rather than the raw value; the account as stated assumes ordinary integer equality and treats NULL as never matching.

7. **Residual uncertainty about interpreter behavior.** The account specifies state and rules but does not claim a specific external interpreter will reproduce them. If an interpreter is later supplied, it must be checked against §4 case by case; in particular it must not conflate `V_R(k) = \emptyset` (absent key) with a present key of empty bag, and it must not "helpfully" match NULL keys.

## 7. Summary of invariants

At every moment between events, the following hold:

- For every `lid ∈ Dom(L)`, \(m_L(\mathrm{lid}) = |V_R(k_L(\mathrm{lid}))|\) when \(k_L(\mathrm{lid}) \neq \mathrm{NULL}\), and \(m_L(\mathrm{lid}) = 0\) otherwise.
- For every non-NULL `k`, \(\mathrm{LidsForKey}(k) = \{\mathrm{lid} : k_L(\mathrm{lid}) = k\}\).
- The output bag equals the union over `lid ∈ Dom(L)` of \(\{(\mathrm{lid}, k_L(\mathrm{lid}), v) : v \in V_R(k_L(\mathrm{lid}))\}\) when \(m>0\), plus \(\{(\mathrm{lid}, k_L(\mathrm{lid}), \mathrm{NULL})\}\) when \(m=0\), with multiplicity inherited from the bag \(V_R\).

Given these invariants, each event rule in §4 preserves them, and the per-event output deltas exactly track the change in the union. That is the account.
