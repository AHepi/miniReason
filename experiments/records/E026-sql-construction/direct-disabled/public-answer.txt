We need maintain the exact result bag of:

```sql
SELECT ALL L.lid, L.k, R.v
FROM L LEFT JOIN R ON L.k = R.k;
```

Target row shape is `(lid, k, v)`, where `lid` always comes from `L`, `k` is `L.k`, and `v` is either a matched `R.v` or SQL `NULL` when no matching right row exists.

Because `ALL` is used, multiplicity matters. In particular:

- Each `L` row contributes at least one output row.
- If one `L` row matches \(m\) right rows, it contributes \(m\) output rows.
- If one `L` row matches zero right rows, it contributes exactly one output row with `v = NULL`.

A nullable key complicates matters: SQL equality `L.k = R.k` is not true when either side is `NULL`. Thus:

- `L.k IS NULL` never matches any `R` row, even `R.k IS NULL`.
- `R.k IS NULL` never matches any `L` row.
- Nullable `v` is not used in the join and is copied directly.

So the essential task is to maintain, for each `L` row, its multiplicity contribution, and for each non-null left key, the bag of matching right rows’ `v` values.

A reusable incremental account can be built around keyed indexes and per-row counts. The following is one sufficient construction.

---

## 1. Retained state

Maintain four logical components.

### 1.1 Left-row map

Map:

\[
L_{\text{row}} : \text{lid} \mapsto (k, A)
\]

where:

- `lid` is the primary key of `L`;
- `k` is the current left key, possibly `NULL`;
- `A` is the number of output rows generated for this left row if it is treated as having no right matches? More precisely, store enough to know its current contribution.

Better: store for each `lid`:

\[
L_{\text{row}}[\text{lid}] = (k, m)
\]

where \(m\) is the number of current matching right rows for this left key, if `k IS NOT NULL`; and \(m = 0\) if `k IS NULL`.

Then the output multiplicity contribution of this `L` row is:

\[
\max(m,1)
\]

because `LEFT JOIN` produces one null-extended row when \(m=0\), and \(m\) rows when \(m>0\).

But to produce the actual `v` values, we also need the matching right values. So this map alone is not enough.

### 1.2 Non-null left-key index

For each non-null left key value \(k\), maintain the set of `L.lid` rows currently having that key:

\[
L_{\text{key}}[k] = \{\text{lid} \mid L_{\text{row}}[\text{lid}].k = k\}
\]

This is only for \(k \neq NULL\). Null left keys are tracked separately or simply by the per-row map.

### 1.3 Right rows by key

For each right key value \(k\), including possibly `NULL`, maintain the bag of right rows:

\[
R_{\text{key}}[k] = \text{multiset of }(\text{rid}, v)
\]

Actually only `v` matters for output, but `rid` is needed for deletion. So retain:

\[
R_{\text{byKey}}[k] = \{(\text{rid}, v)\}
\]

For \(k = NULL\), these rows never match any left row under ordinary SQL equality. They may still be retained for correctness of deletion and to know they produce no output. They are needed only because a later delete event may remove them.

Also maintain a direct right-row lookup:

\[
R_{\text{row}}[\text{rid}] = (k, v)
\]

so a deletion can find and remove the row from the correct key bucket.

### 1.4 Output bag representation

To support exact result maintenance, retain the current output as a bag. Since row order is immaterial, represent it as a multiset of triples:

\[
O = \{( \text{lid}, k, v )\}
\]

with multiplicity. Equivalently, group by `lid` and current contribution:

- For each left row with `k IS NULL`: exactly one output row `(lid, NULL, NULL)`.
- For each left row with non-null \(k\):
  - if \(R_{\text{byKey}}[k]\) is empty: one output row `(lid, k, NULL)`;
  - otherwise: for each `(rid, v)` in \(R_{\text{byKey}}[k]\), one output row `(lid, k, v)`.

This is the complete result state. The maps above are sufficient to update it incrementally.

---

## 2. Initialization

Initialization reads the initial `L` and `R` tables once.

Build:

1. For every `L` row `(lid, k)`:
   - insert `lid -> (k, 0)` into `L_row`;
   - if `k IS NOT NULL`, add `lid` to `L_key[k]`.

2. For every `R` row `(rid, k, v)`:
   - insert `rid -> (k, v)` into `R_row`;
   - add `(rid, v)` to `R_byKey[k]`, including when `k IS NULL`.

3. Compute the initial output bag `O`.

For each left row `(lid, k)`:

- If `k IS NULL`:
  - add one row `(lid, NULL, NULL)` to `O`.
  - set its match count \(m=0\).
- If `k` is non-null:
  - let \(B = R_byKey[k]\).
  - if \(B\) is empty:
    - add `(lid, k, NULL)` to `O`.
    - set \(m=0\).
  - else:
    - for each `(rid, v)` in \(B\), add `(lid, k, v)` to `O`.
    - set \(m = |B|\).

Store \(m\) in `L_row[lid]`, or compute it from `R_byKey[k]` whenever needed. Either is acceptable; storing it can make updates faster but is redundant if `R_byKey` is always current.

After initialization, the original tables and history are not needed. The retained maps and output bag are sufficient.

---

## 3. Event handling

Events are inserts and deletes for `L` and `R`. Updates are delete-then-insert and are handled as two separate events.

For each event, identify the affected left key or right key, and update only the output rows whose `lid` belong to left rows with that key, or whose right row was inserted/deleted.

The key observation is:

- An insertion or deletion in `L` affects exactly the output rows for that one `lid`.
- An insertion or deletion in `R` with non-null key \(k\) affects exactly the output rows for all left rows whose key is \(k\).
- An insertion or deletion in `R` with `NULL` key affects no output rows directly, because `R.k IS NULL` never satisfies `L.k = R.k`.

---

## 4. Insert into L

Event: insert left row `(lid, k)`.

Precondition: `lid` is absent from `L_row`.

Steps:

1. Add `lid -> (k, 0)` to `L_row`.
2. If `k IS NOT NULL`, add `lid` to `L_key[k]`.

3. Determine output rows for this new left row.

Let \(B = \varnothing\) if `k IS NULL`, else \(R_byKey[k]\).

- If `k IS NULL` or \(B = \varnothing\):
  - insert one output row `(lid, k, NULL)` into `O`.
  - set match count \(m=0\).
- Else:
  - for each `(rid, v)` in \(B\), insert `(lid, k, v)` into `O`.
  - set match count \(m=|B|\).

No other output rows change.

If `k IS NULL`, the inserted output row is `(lid, NULL, NULL)`.

Multiplicity: Exactly one output row if no match; exactly \(|B|\) output rows if matched. No duplicates are created for other `lid` values.

---

## 5. Delete from L

Event: delete existing left row `(lid, k)`.

Precondition: `lid` exists in `L_row`, and its stored key is `k`.

Steps:

1. Remove all output rows with that `lid`.

Because output rows are uniquely identified by `lid` plus the matching right value or null-extension, we can delete:

- If `k IS NULL` or the stored match count was zero:
  - remove the single row `(lid, k, NULL)`.
- Else:
  - for each `(rid, v)` in `R_byKey[k]`, remove one occurrence of `(lid, k, v)`.

2. Remove `lid` from `L_row`.

3. If `k IS NOT NULL`, remove `lid` from `L_key[k]`.

No other output rows change. In particular, deleting one left row does not affect output rows for other left rows sharing the same key.

---

## 6. Insert into R

Event: insert right row `(rid, k, v)`.

Precondition: `rid` absent from `R_row`.

Steps:

1. Add `rid -> (k, v)` to `R_row`.
2. Add `(rid, v)` to `R_byKey[k]`.

3. If `k IS NULL`, no output rows change, because this right row can never match any left row under ordinary equality.

4. If `k IS NOT NULL`, let \(S = L_key[k]\), the set of left rows whose key is exactly \(k\).

For each `lid` in \(S\):

- Let the previous match count for this left row be \(m\). Before this insert, \(m \ge 0\).
- If \(m = 0\), then before the insert the left row contributed one null-extended output row:
  - remove one occurrence of `(lid, k, NULL)` from `O`.
- Add one occurrence of `(lid, k, v)` to `O`.
- Increment the match count for `lid` by 1.

Why this works:

- If this is the first matching right row for that left key, the null-extended row disappears and is replaced by one real matched row.
- If there were already matches, we simply add one more matched row.

No output rows for left keys other than \(k\) change.

---

## 7. Delete from R

Event: delete existing right row `(rid, k, v)`.

Precondition: `rid` exists in `R_row`, and its stored key/value are `k, v`.

Steps:

1. Remove `rid` from `R_row`.
2. Remove one occurrence of `(rid, v)` from `R_byKey[k]`.

3. If `k IS NULL`, no output rows change.

4. If `k IS NOT NULL`, let \(S = L_key[k]\).

For each `lid` in \(S\):

- Remove one occurrence of `(lid, k, v)` from `O`.
- Decrement the match count for `lid` by 1.
- If the new match count is \(0\), then after removing the last matched right row, insert one null-extended output row `(lid, k, NULL)` into `O`.

Why:

- Removing a matched right row removes exactly one corresponding output row per left row with that key.
- If that was the last match for a given left row, `LEFT JOIN` must now produce one null-extended row for that left row.

No output rows for other left keys change.

---

## 8. Null-key cases

### 8.1 `L.k IS NULL`

Such a left row never matches any right row. It always contributes exactly one output row:

\[
(\text{lid}, NULL, NULL)
\]

Insertion or deletion of any right row does not change it.

Deletion of the left row removes that one output row.

### 8.2 `R.k IS NULL`

Such a right row never matches any left row. It contributes nothing to the output.

Inserting or deleting it changes no output rows. It is retained in `R_row` and `R_byKey[NULL]` only because a later delete event may refer to it and because `R` table state must remain accurate if needed for later inserts/deletes. But for the target query, it is output-inert.

### 8.3 `R.v IS NULL`

The value column may be `NULL`. This is not special for matching. If a non-null key matches and `R.v IS NULL`, the output row is `(lid, k, NULL)`. This can be indistinguishable from a null-extended row by value alone, but it is distinguishable by provenance: it is generated by an actual matching right row.

This matters for multiplicity and deletion. For example, if a left row with key \(k\) matches exactly one right row whose `v IS NULL`, the output contains one row `(lid, k, NULL)`. If that right row is deleted, the output still contains one row `(lid, k, NULL)` because the left row becomes unmatched. The visible row is the same, but the reason changes. If another `v=NULL` right row with key \(k\) is inserted, the output now has two `(lid,k,NULL)` rows.

A correct state must therefore distinguish:

- null-extension due to zero matches;
- an actual matched right row with `v=NULL`.

Retaining match counts and right-row identities handles this. A representation that only stores the visible output bag may still be sufficient if it also stores enough provenance to know whether a `(lid,k,NULL)` row is a null-extension or a real match. Otherwise, deleting a real `v=NULL` match could be mishandled.

---

## 9. Output change summary by event type

Let \(k\) be the affected key.

### Insert L `(lid, k)`

- If `k IS NULL`: add `(lid, NULL, NULL)`.
- Else if no right rows with key \(k\): add `(lid, k, NULL)`.
- Else: add `(lid, k, v)` for each right row with key \(k\).

### Delete L `(lid, k)`

- Remove exactly the output rows whose `lid` is `lid`.
- Those are either one null-extended row or one row per matching right row.

### Insert R `(rid, k, v)`

- If `k IS NULL`: no output change.
- Else for each left row with key \(k\):
  - if it previously had zero matches, remove its null-extended row;
  - add one `(lid, k, v)` row.

### Delete R `(rid, k, v)`

- If `k IS NULL`: no output change.
- Else for each left row with key \(k\):
  - remove one `(lid, k, v)` row;
  - if that left row now has zero matches, add one `(lid, k, NULL)` row.

---

## 10. Invariants

A correct maintained state should satisfy:

1. `L_row` is a bijection between current `L` rows and stored `(k, m)` pairs.
2. `R_row` is a bijection between current `R` rows and stored `(k, v)` pairs.
3. For every non-null key \(k\):
   - `L_key[k]` equals the set of `lid` whose current left key is \(k\).
   - `R_byKey[k]` equals the bag of current right rows whose key is \(k\).
4. For each `lid` with non-null key \(k\):
   - stored match count \(m = |R_byKey[k]|\).
5. The output bag \(O\) equals:
   - one `(lid, NULL, NULL)` for each left row with `k IS NULL`;
   - for each left row with non-null \(k\):
     - if `R_byKey[k]` is empty, one `(lid, k, NULL)`;
     - otherwise, one `(lid, k, v)` for each `(rid, v)` in `R_byKey[k]`.

These invariants are preserved by the update rules above.

---

## 11. Whole-database recomputation alternative

A simpler but non-incremental alternative is to retain the full current `L` and `R` tables, or sufficient copies, and after each event recompute:

```sql
SELECT ALL L.lid, L.k, R.v
FROM L LEFT JOIN R ON L.k = R.k;
```

That is correct for arbitrary finite tables and legal events. However, it is outside the requested incremental-use contract because it does not use affected keys to derive output changes; it recomputes the whole output. It may still be useful as a fallback or as a verification oracle.

A middle ground is to retain the full `L` and `R` state and recompute only the affected group. For example, after an `R` insert/delete with non-null key \(k\), recompute all output rows for left rows with key \(k\). This is incremental in the sense of restricting to affected keys, though not minimal. The rules above give a finer per-row update.

---

## 12. Unsupported cases and uncertainty

The construction assumes the stated value domain:

- `lid` and `rid` are unique signed 32-bit integers within each table.
- Keys are signed 32-bit integers or SQL `NULL`.
- Values are Unicode strings or SQL `NULL`.

It assumes events are legal:

- Insert IDs are absent.
- Delete before-images correspond to existing rows.
- Updates are modeled as delete followed by insert.

It assumes ordinary SQL equality semantics, where `NULL = anything` is not true.

Uncertainty:

- If the implementation treats `NULL` keys specially, or if the join condition were changed to `IS NOT DISTINCT FROM` or `IS`, the null-key rules would differ. Under the supplied SQL, null keys never match.
- If duplicate `lid` or `rid` values could occur, the primary-key assumption would be violated, and the maps would need bag semantics for IDs.
- If there were non-deterministic collation or type coercion between integer keys, matching could differ. The domain states signed 32-bit integers, so exact integer equality is assumed.
- If the output order were required, additional order-maintenance state would be needed. The problem states row order is immaterial.
- If `SELECT ALL` were replaced by `SELECT DISTINCT`, multiplicities would collapse and the update rules would need a separate distinct-bag maintenance layer. The supplied query uses `ALL`, so duplicates are retained.

Within those assumptions, the retained state and update rules above maintain the exact result bag after each event without accessing the original database after initialization.
