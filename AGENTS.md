# Agent entry point

Before choosing an execution strategy, root and every subagent must read the repository [miniReason experiment operations skill](skills/minireason-experiment-operations/SKILL.md) and consult its [recorded failure guide](docs/errata/REC-20260913-windows-execution.md). The repository copy remains available when personal skill discovery is unavailable. Apply current user instructions over historical incident guidance; the single publisher does not require serial model execution across independent arms.

Use the installed personal skill **minireason-progress-ledger** for active continuation. Complete a verified push to main at least every five minutes during active work, independently of the substantive-ledger clock, and still publish every completed document immediately. Use the skill's separate publication acknowledgement with actual remote/local commit and equal-tree verification; a local append cannot reset the push deadline. Before a potentially long evidence upload, publish a small reviewed progress checkpoint first and leave time for verification. A partial upload is not a push; record a missed deadline truthfully and recover it. Write a substantive UTC progress/decision receipt at least every five minutes and sooner for completed documents or material changes; activity-log events alone do not satisfy this requirement. Start its session-local timer after an opening receipt, check it at tool boundaries, and acknowledge only a newly appended substantive receipt. It warns at 240 seconds and marks 300 seconds overdue. The skill helper cannot wake an inactive conversation or guarantee a deadline during a blocked tool. Record a missed deadline truthfully, never backdate it. Locate the skill by its exact frontmatter name if its installation directory changes. If temporarily unavailable, continue with explicit elapsed-time checks and the same ledger cadence; do not stop otherwise authorized research merely because the reminder is unavailable.

Read [docs/DECISION_LEDGER.md](docs/DECISION_LEDGER.md) first, then [README.md](README.md), [PURPOSE.md](PURPOSE.md), [docs/STATUS.md](docs/STATUS.md) and the relevant [workflow](docs/workflows/README.md) before acting. After an interruption, use [the continuation and recovery workflow](docs/workflows/continue.md) to locate the last verified remote checkpoint and any unpublished or partial work. The user has explicitly authorised extraction from AHepi/h-EPI and commits and pushes to AHepi/miniReason `main`, including running decision-ledger checkpoints and publication after each configuration test. Keep the source repository unchanged.

Every design, implementation, experiment, interpretation, delegation, publication and stopping decision must have an append-only receipt in the ledger before action: choice, reason, contribution to the end goal, and pending or completed state with evidence. Append dated outcomes and corrections; do not rewrite earlier receipts. Record mechanical executions under the decision they implement. Keep public justifications concise. Every agent must continuously log each repository or staging search, read, modification and test in docs/AGENT_ACTIVITY.jsonl using tools/repo_activity.py before execution and with its outcome. The activity logger uses atomic locked appends; agents may append there without editing the decision ledger. Record a specific action, relevant paths, why and goal; never log credentials or raw secret-bearing command text. The single publisher owns decision-ledger edits and publication when agents work concurrently; delegated agents supply their decision receipts to that publisher before acting on a new choice. Publish every completed document to main immediately: review it, commit its explicit path with supporting ledger/current STATUS receipts, publish non-forcibly, and verify remote main and the exact tree before proceeding to another document. This includes reviews and reports and applies independently of configuration completion. Do not batch completed documents for a later experiment checkpoint. Preserve recovered partial drafts unchanged and publish completion supplements separately. Publish small reviewed checkpoints so receipts and recoverable work survive another failed window. Update STATUS with what actually completed and the next authorized task.

Use the user-designated FW5 explanatory-construction reading edition as the current semantic source, with source identity and obligations in docs/SEMANTIC_GUIDE.md. ECS 2.0 is a separately identified successor whose additions remain hypotheses; historical frozen studies retain their original sources. Harness spec v1.3 is a mechanism guide. Neither old source-project authority nor executable success silently redefines these sources. Keep prose conjectures and criticisms legitimate; syntax and executable tests cannot be made the definition of bearing or creativity.

Respect the comparison: bare, native reasoning and Mini under declared information and resource conditions. Add matched multi-call controls when interpreting an advantage of extra calls. Preserve actual wire requests, final answer text, token counts, provider identity, settings, configurations and checker identity. Never store API credentials or native hidden reasoning text. Read DEEPSEEK_API_KEY only at call time.

No random configuration mutation, automatic evolutionary optimisation or scalar progress meter. Deliberate task instance generation or arm ordering must state its purpose and seed. Do not let an operational alarm adjudicate content. Every failure receives an erratum with evidence and every transferable lesson enters its appropriate lesson file.

Never modify a published observation. Preserve partial reports and interrupted evidence unchanged; later completion reviews or corrected interpretations go in separately named files identifying their sources and limits. Do not omit unsuccessful experiments. Stage explicit reviewed paths, scan for credentials, run relevant verification, commit and push normally to `main`, and verify the remote commit and tree. If the authenticated connector creates a different commit, verify that its tree exactly matches the intended local checkpoint and record both commit identities, the shared tree, and remote-main confirmation. No force push or rewriting history. At most five live config tests concurrently. One publisher serialises commits; a run's completed record is published and verified before successor work starts. A failed or partial publication remains pending until that verification succeeds.

Stop only with an honest reason: a documented evidential judgement about explored mechanisms, or a concrete external blocker. A token/call/time ceiling is a resource boundary and must not be described as exhaustion. Record what would justify reopening the inquiry.
