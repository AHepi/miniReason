# Self-piloting feasibility

**POSSIBLE WITH PROBED FEATURES.** Flash can plausibly choose and fill bounded templates and request sub-calls through a host-controlled protocol. The requested records establish several usable component roles; they do not demonstrate a reliable autonomous pilot. A model emits requests: the harness must authorize, dispatch, record and verify them. No plugin was built and no live probe was executed in this study.

This verdict means interface and role feasibility justify preparation, with a qualification gate before implementation. It does not mean the missing probes have passed. A JSON-object control envelope is possible with the existing API; function-call control requires a new response adapter because the current text transport discards tool calls. The official docs support tool calls and beta strict argument schemas, so no documented API impossibility blocks the design. See [CAPABILITY](CAPABILITY.md) for all denominators and [API-NOTES](API-NOTES.md) for exact official URLs read 2026-09-17.

## Minimum viable pilot loop

1. **Seal task and constraints.** Host records exact task/source bytes, allowed output paths and tools, template catalogue/version, model/settings, checker identities and a declared budget. It assigns a run ID and refuses replay of existing attempts.
2. **Choose template.** One thinking-disabled Flash call selects one of five registry IDs and provides a short reason. Host checks the enum, inputs, scope and resource envelope. Unsupported/missing inputs return cannot_decide; no invented template is dispatched.
3. **Request sub-calls.** Pilot emits a bounded DAG with child template IDs, exact input/source references, output contracts and dependencies. Host rejects cycles, unknown references, unsupported modes and over-budget work. Only dependency-ready calls run, at most five concurrently. A narrower task must require a result, not merely rename the overall task.
4. **Validate and assemble.** Each worker's public result is recorded before it is checked. Invalid JSON/schema can receive one separately recorded repair with the original public response and exact checker detail. Failure/partial/unknown remains visible. Assembly may use only accepted dependencies and must disclose contradictions and uncompleted work.
5. **Verify and stop.** Host checks exact references and deterministic propositions; an independent critic may challenge the argument. A model's statement that tests passed is not a test receipt. Final status is complete only for satisfied obligations, otherwise partial/cannot_decide/failed. A budget stop describes a resource boundary, not exhausted research.

[ROUTER-DESIGN](ROUTER-DESIGN.md) provides the catalogue, routing rules, function parameter contracts, ceilings, conditional price envelopes and recovery protocol. The pilot cannot edit its authorization, mark publication verified, bypass a failed dependency or promote its own judgment to an oracle.

## Custody and failure containment

Preserve the actual sent wire bytes and hash, source/template/schema/checker hashes, requested and returned provider/model identities, settings, public answers/tool arguments, response digest, token usage, epochs, latency and every failed attempt. Missing usage remains unknown. Native hidden reasoning and credentials are never persisted. R002's historical prepared/sent serialization-order discrepancy is explicitly retained; the new probe serializes once and sends those exact hashed bytes.

Control/tool turns use thinking off. The current official thinking guide requires replaying hidden reasoning across tool-bearing conversations; durable replay would violate this repository's custody rule. Native reasoning is confined to separate no-tools worker calls whose public answers can return to the pilot. The 4096-token pair probes mode handling on one short task, not long-derivation adequacy.

API tool/strict claims need live confirmation: ordinary and strict two-tool schemas, valid arguments, matching result IDs and voluntary stopping. The five routing tasks and one spawn test establish only elementary planning shape. They do not establish robust delegation quality or a production failure rate. One successful tool continuation cannot validate unlimited recursion.

Open risks remain: exhaustion on long derivations; complex prose-contract brittleness; wrong criticism and harmful uptake; uncompleted synthesis; source instructions contaminating task authority; prompt growth; timeout or unknown-spend recovery; provider alias/price changes; and unqualified Windows durability for any full scheduler reused from earlier work. A future harness must qualify its actual persistence route rather than assume filesystem writes alone prove crash recovery. Probe write-once records are evidence capture, not that scheduler qualification.

For any claimed advantage over bare/native reasoning, add matched multi-call controls with declared information and resources. R001/R002 do not establish loop superiority; R003 proposal differences do not establish a propagated correction. Syntax and execution cannot decide the FW5 account or make prose criticism illegitimate.

## Qualification and reopening

The prepared probes are the next smallest discriminating action, executed only by the orchestrator. Passing all probes permits a separately authorized minimal harness implementation and end-to-end fixtures; it does not close the capability study. Failures should choose a documented JSON-envelope fallback or a specific contract/transport correction, followed by new identified trials, rather than unbounded retries.

Reopen for probe outcomes, a concrete census/custody defect, changed official API behavior, or authorization for integrated pilot tasks with correctness and recovery checks. This run stops at a completed preparation handoff, not at an evidential claim that the inquiry is exhausted.
